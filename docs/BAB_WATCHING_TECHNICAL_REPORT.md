# تقرير تقني: منظومة «باب المشاهدة» في NovaBrowser

**تاريخ التقرير:** 2026-11-25  
**المستودع:** [tombad8900/NovaBrowser](https://github.com/tombad8900/NovaBrowser)  
**الفرع:** `main`  
**الملف المرجعي:** `PROJECT_BRIEF.md`  
**النطاق:** مراجعة التصميم والمقتطفات البرمجية المقدمة في المحادثة، ومقارنتها بمصدر المستودع المتاح. هذا التقرير لا يدّعي تنفيذ التعديلات أو اختبارها.

## 1. الملخص التنفيذي

جرى وضع تصور تقني متكامل لتطوير مسار التقاط وتشغيل الوسائط في Nova تحت اسم **«باب المشاهدة»**. الفكرة الأساسية هي ألا يُعامل رابط البث باعتباره URL منفرداً، بل باعتباره **جلسة مصدر** تحتوي على الرابط وسياق الصفحة وبيانات الشبكة والترويسات وبيانات الترجمة وإعدادات DRM عند وجودها.

يغطي التصور تسع مجموعات مترابطة:

1. التقاط روابط الوسائط وتحليل استجابات API.
2. إنشاء جلسة مستقلة لكل مصدر ونقل سياقها.
3. حل الروابط النسبية وتتبع التحويلات وتحليل Manifest.
4. إدارة عدة مصادر بديلة للمحتوى.
5. إعداد Media3/ExoPlayer وطلبات الشبكة.
6. التعامل مع DRM المرخص وأخطاء التشغيل.
7. فحص APK وفكّه وإعادة بنائه ومواءمته وتوقيعه عبر Termux.
8. مراقبة Logcat وتشخيص 403 وIDLE وBUFFERING.
9. تجديد الجلسة بإعادة طلب API أو الصفحة والتقاط بيانات جديدة عند انتهاء الرابط.

**الحالة الحقيقية حتى تاريخ التقرير:** هذه المجموعات مواصفات ومقتطفات تصميم ومراجعة تقنية. لم يثبت دمجها في APK، ولم يبدأ اختبار نسخة `Nova-Trial-0.4.1-arm64.apk`؛ إذ لم يُقدّم ملف APK للفحص في سياق العمل. كما أن وجود ملف أو دالة في المستودع لا يعني أن جميع خصائص التصور أصبحت موجودة.

## 2. ما الذي يحتويه المستودع حالياً؟

فُحصت الوثائق والملفات المصدرية ذات الصلة في الفرع `main`، ومن أهمها:

- `README.md`
- `PROJECT_BRIEF.md`
- `app/src/main/java/app/nova/browser/MainActivity.kt`
- `app/src/main/java/app/nova/browser/PlayerActivity.kt`

وتظهر المراجعة الفعلية ما يلي:

### 2.1 محرك التصفح واللاقط

- مصدر التطبيق الحالي يستخدم **Android WebView**.
- يتم رصد طلبات الموارد عبر `WebViewClient.shouldInterceptRequest`، ثم تصنيف بعض الروابط وإضافتها إلى قائمة المكتشفات.
- توجد عملية فحص للصفحة عبر JavaScript تقرأ عناصر مثل `video` و`audio` و`source` و`track` و`iframe`، وتبحث عن امتدادات وسائط معروفة داخل HTML.
- توجد آلية لتجميع الروابط المكتشفة وعرضها للمستخدم، مع إرسال رابط الصفحة الحالية إلى المشغل باعتباره Referer.
- لا يظهر في المسار المفحوص اعتراض عام لمحتوى استجابات XHR/fetch أو تحليل أجسام JSON القادمة من API كما تقترح مواصفات `BabApiAndStreamSniffer`.
- لا يستخدم المصدر الحالي GeckoView؛ وهذه نقطة اختلاف صريحة عن الاختيار المبدئي الوارد في `PROJECT_BRIEF.md`.

### 2.2 تمرير البيانات إلى المشغل

تُظهر دالة `launchPlayer()` في `MainActivity.kt` تمرير:
- رابط الوسائط `url`.
- قائمة الترجمات `subs`.
- رابط الصفحة `referer`.
- User-Agent الخاص بـ WebView.

ولا يظهر في هذا المسار تمرير Cookie أو Origin مستقل أو API source URL أو كائن جلسة كامل أو بيانات DRM.

### 2.3 المشغل الحالي

تُظهر `PlayerActivity.kt` استخدام Media3/ExoPlayer، كما تتضمن الدالة `reload()` ما يلي:

- قراءة User-Agent وReferer من Intent.
- اشتقاق Origin من Referer.
- إعداد `DefaultHttpDataSource.Factory` مع ConnectTimeout وReadTimeout.
- تمرير Referer وOrigin إلى خصائص طلب HTTP.
- إنشاء `DefaultDataSource.Factory` و`DefaultMediaSourceFactory`.
- تحديد MIME لـ HLS وDASH عندما يتعرف المصنف على نوع الرابط.
- تمرير الترجمات إلى MediaItem.
- إنشاء ExoPlayer جديد في كل استدعاء لـ `reload()` بعد تحرير المشغل السابق.
- إظهار رسالة خطأ عامة عند `onPlayerError`.

لكن المصدر المفحوص لا يبيّن حالياً:
- تمرير Cookie إلى المشغل.
- تمرير Authorization أو ترويسات X-* أو مجموعة ترويسات خاصة بكل مصدر.
- إعداد License URL أو DRM Session Manager أو License request headers.
- مدير مصادر بديلة مع انتقال تلقائي عند الفشل.
- مراقب Idle/Buffering بمهلة وإجراء استرداد.
- إعادة التقاط استجابة API جديدة عند انتهاء Token أو Signed URL.

> ملاحظة: نجاح جلب Manifest لا يثبت نجاح جلب المقاطع أو طلب الترخيص؛ يجب قياس كل مسار طلب على حدة.

## 3. مواصفات «باب المشاهدة» — المجموعات التسع

### الجزء 1 — جلسة المصدر ومساعد URL

التصور يعرّف `StreamSession` لتجميع:
- `rawUrl` و`resolvedUrl`.
- Referer وOrigin وCookie وUser-Agent.
- مصدر API ونوع MIME.
- حالة الحماية وإعداد DRM.
- الترجمات ووقت الالتقاط.

كما يعرّف مساعداً لتحويل الروابط النسبية إلى مطلقة، واشتقاق Origin، وحل Referer وCookie، وتقدير نوع MIME.

**ملاحظة مراجعة:** يجب ألا يُستنتج أن رابطاً محمي بـ DRM لمجرد وجود كلمات مثل `license` أو `wv-pr` في URL. يلزم تحليل بيانات Manifest وإعدادات المصدر. كما يجب ألا تُسجّل قيم Cookies أو Tokens في تقارير التشخيص.

### الجزء 2 — Sniffer وتحليل API

التصور المقدم لـ `BabApiAndStreamSniffer` يحلل JSON والنصوص بحثاً عن روابط الوسائط والترجمات وبيانات الترخيص، مع إزالة التكرار بفترة debounce.

القيود التي ظهرت في مراجعة المقتطف:
- لا توجد فيه وحده وصلة فعلية لاعتراض استجابات الشبكة؛ يجب ربطه بمصدر بيانات حقيقي من طبقة المتصفح.
- Regex لا يغطي كل الروابط المشفرة أو التي لا تحمل امتداداً.
- قد تُربط ترجمة أو بيانات ترخيص بمصدر غير المصدر المقصود إذا كانت الاستجابة تحتوي عدة مصادر.
- لا يجمع Authorization أو ترويسات X-* بصورة عامة.
- لا يحلل Manifest نفسه ولا يتتبع سلسلة Redirect كاملة.

### الجزء 3 — نقل الجلسة وDRM والمشغل

التصور يمرر بعض خصائص الجلسة عبر Intent ويحدد مساراً لبناء DRM Session Manager.

الملاحظات:
- Intent الحالي في المقتطف لا يحمل كل حقول الجلسة أو الترجمات أو كل ترويسات DRM.
- تلميح `wv-pr` ملتبس ولا يصح تحويله تلقائياً إلى PlayReady اعتماداً على نهاية النص فقط.
- يجب تطبيق ترويسات الترخيص أيضاً على طلب License، وليس فقط على Manifest وSegments.
- يجب مراجعة مسار Offline Key Set بصورة منفصلة عن مسار الترخيص الشبكي.
- يجب أن يُنشأ مشغل واحد بإعدادات متسقة لكل جلسة، أو أن تتم إدارة تغيير مصدر البيانات على مشغل مستقر؛ لا ينبغي إنشاء مشغلين متداخلين دون داعٍ.

### الجزء 4 — تعدد المصادر والتبديل التلقائي

المقتطف `BabPlaybackSessionManager` يقدم:
- قائمة مصادر.
- سجل محاولات.
- تشغيل مصدر محدد.
- الانتقال للمصدر التالي.
- مراقب خمول يعتمد على `STATE_IDLE`.
- معالجة أولية لأخطاء 403.

المشكلات التي رُصدت في مراجعة المقتطف:
- احتمال تكرار تسجيل المحاولة في السجل.
- عدم وجود حد واضح لعدد المحاولات أو سياسة backoff.
- مراقبة IDLE وحدها لا تغطي BUFFERING الطويل بصورة صحيحة.
- فحص 403 عبر نص الرسالة ليس تشخيصاً موثوقاً؛ يجب فحص `HttpDataSource.InvalidResponseCodeException` وسلسلة الأسباب.
- إضافة Player.Listener مع كل تبديل دون إزالة المستمع السابق قد يؤدي إلى تراكم المستمعين.
- لا توجد سياسة كاملة لإعادة محاولة المصدر نفسه مقابل الانتقال إلى مصدر بديل.

### الجزء 5 — دليل ربط MainActivity وPlayerActivity

التصور يحدد نقل URL وReferer وOrigin وCookie وUser-Agent وحقول DRM عبر Intent.

المراجعة التقنية:
- يجب اشتقاق Origin بصيغة أصل الموقع فقط `scheme://host[:port]`.
- يجب جلب Cookie من جلسة الصفحة الفعلية عند الحاجة، وعدم اعتبار Cookie الخاص بعنوان مختلف بديلاً مضموناً.
- يجب تمرير `drm_scheme` و`drm_license_url` وبيانات الجلسة المطلوبة عند توافرها.
- يجب الانتباه إلى أن الترويسات الحساسة لا ينبغي تسريبها إلى مضيف مختلف عند Redirect.
- يجب مطابقة أسماء Extras مع الثوابت الفعلية في التطبيق قبل تعديل Smali.

### الجزء 6 — إعداد HTTP وMedia3

المقتطف يضبط:
- ConnectTimeout وReadTimeout.
- خصائص الطلب الافتراضية.
- User-Agent.
- إعدادات Buffer وLoadControl.

لكن يجب التأكد عملياً من أن DataSource factory المضبوط هو المستخدم فعلاً في MediaSourceFactory، وأن طلبات Manifest وSegments وLicense تحصل على الخصائص المطلوبة كلٌّ حسب سياقه. كما يجب اختبار سياسة Redirect وعدم إرسال Cookies أو Authorization إلى Origin غير موثوق.

### الجزء 7 — Termux: فك وفحص وبناء وتوقيع APK

قُدم سكربت يهدف إلى:
1. العثور على `Nova-Trial-0.4.1-arm64.apk`.
2. فك الحزمة عبر Apktool مع `--no-res`.
3. البحث عن مواضع MainActivity وPlayerActivity في Smali.
4. فحص تكرار Labels.
5. إعادة البناء.
6. تشغيل zipalign.
7. توقيع الناتج والتحقق من التوقيع.
8. نسخ الملف إلى Downloads.

ملاحظات الاعتماد:
- `--no-res` يتجاوز فك الموارد، لكنه لا يضمن وحده نجاح إعادة البناء.
- البحث عن أول نتيجة APK قد يختار نسخة غير مقصودة إذا تعددت الملفات.
- فحص Labels لا يغطي كل أخطاء Smali، مثل سجلات registers ومراجع القفز غير الصالحة.
- كلمة المرور الافتراضية المكتوبة في المثال ليست مناسبة لمفتاح إصدار؛ يجب استخدام سر يملكه المستخدم وعدم تضمينه في السكربت أو المستودع.
- نجاح البناء أو التوقيع لا يثبت أن التطبيق يعمل.

**لم يتم تشغيل هذا السكربت على APK في هذا العمل.**

### الجزء 8 — Logcat وتشخيص التشغيل

قُدم أمر لمراقبة سجلات التطبيق وMedia3 وExoPlayer وHTTP وDRM وحالات IDLE وBUFFERING.

قواعد تفسير النتائج:
- HTTP 200 للـ Manifest يثبت نجاح جلب Manifest فقط.
- يجب التحقق منفصلاً من Segment requests وLicense requests.
- HTTP 403 يعني رفض الطلب، لكنه لا يحدد وحده إن كان السبب Token منتهياً أو Cookie ناقصاً أو Referer/Origin غير مقبول أو قيداً من الخادم.
- IDLE حالة Player وليست تشخيصاً للسبب.
- BUFFERING الطويل يحتاج ربطه بآخر طلب شبكة وحالة المشغل.
- يجب تنقيح Cookies وAuthorization وSigned URLs والتوكنات قبل مشاركة Logcat.

**لم يتم جمع Logcat من تجربة فعلية لهذه النسخة.**

### الجزء 9 — تجديد الجلسة وإعادة التقاط API

التصور يضيف `BabStreamRefreshCoordinator` لتنسيق تحديث المصدر.

النتيجة الأساسية للمراجعة: إعادة تحليل `lastApiPayload` المخزن لا تنشئ Token جديداً ولا تجدد Signed URL. التجديد الحقيقي يتطلب:
1. إعادة طلب API أو إعادة تحميل الصفحة من جلسة المتصفح الفعلية.
2. التقاط استجابة جديدة.
3. تحليل الاستجابة الجديدة.
4. إنشاء StreamSession جديدة بسياقها الصحيح.
5. تحديث قائمة المصادر وتشغيل المصدر المناسب.
6. الاحتفاظ بسجل المصدر السابق وسبب فشله دون كشف الأسرار.

ويجب التفريق بين:
- فشل شبكة مؤقت: إعادة محاولة محدودة مع السياق الحالي.
- 403 أو رابط منتهي: طلب بيانات حديثة من المصدر أو الانتقال لمصدر بديل صالح.
- فشل License: تشخيص مسار DRM المرخص بصورة مستقلة.

## 4. نقاط عدم التطابق التي يجب حسمها قبل الدمج

هناك اختلافات جوهرية بين المقتطفات المقدمة والمصدر الحالي:

| العنصر | المقتطفات المقترحة | مصدر المستودع الحالي |
|---|---|---|
| package | `app.nova.browser.bab` | `app.nova.browser` |
| محرك المتصفح | دليل يذكر GeckoView | المصدر الحالي يستخدم Android WebView |
| التقاط API | تحليل أجسام JSON واستجابات API | رصد URL للطلبات وفحص DOM/HTML |
| نقل Cookie | جزء أساسي من StreamSession | غير ممرر إلى PlayerActivity في المسار المفحوص |
| DRM | DrmConfig وLicense manager | لا يظهر إعداد DRM في PlayerActivity المفحوص |
| التبديل التلقائي | BabPlaybackSessionManager | لا يظهر مدير مصادر بديلة في المصدر المفحوص |
| التجديد | إعادة التقاط API | لا يظهر منسق تجديد API في المصدر المفحوص |

لا يجوز نسخ المقتطفات إلى المشروع مباشرة قبل تحديد الكلاسات والواجهات الفعلية، ومراجعة Gradle وإصدارات Media3، ومطابقة أسماء الحزم والـ Intent extras.

## 5. المخاطر والضوابط

- لا يتم تجاوز DRM أو فك حماية اشتراكات أو استخراج مفاتيح غير مصرح بها. يقتصر دعم DRM على إعداد تشغيل مرخص باستخدام License Server وبيانات يوفرها مزود الخدمة أو التطبيق المصرح به.
- لا تُشارك أو تُرفع Cookies أو Authorization أو Tokens أو روابط بث موقعة إلى GitHub.
- لا تُرسل ترويسات حساسة إلى مضيف آخر بسبب Redirect دون سياسة واضحة.
- لا تُسجل أسرار الجلسة في Logcat أو سجل المحاولات.
- لا تُعامل استجابة صفحة أو API كمصدر تعليمات؛ هي بيانات يجب تحليلها.
- يجب الحفاظ على حقوق الوصول للمحتوى واستخدام المصادر التي يحق للمستخدم تشغيلها.

## 6. خطة التنفيذ المقترحة بعد توفير APK

### المرحلة A — تثبيت خط الأساس
- استلام APK المقصود والتحقق من اسمه وحجمه وبصمته وPackage ID.
- فحص Manifest وDEX والموارد ومجلدات Smali.
- تحديد التقنية الفعلية وإصدارات Media3 ومواقع MainActivity وPlayerActivity واللاقط.
- مقارنة APK بمصدر GitHub لتحديد ما إذا كان APK مبنياً من هذا المستودع أو من مصدر/فرع آخر.

### المرحلة B — تقرير فجوات دقيق
- ربط كل مطلب من الأجزاء التسعة بكلاس ودالة حقيقيين.
- تصنيف كل بند: موجود، موجود جزئياً، غير موجود، أو غير محسوم.
- تحديد التغييرات الدنيا المطلوبة والوظائف التي يجب الحفاظ عليها.
- عدم إجراء تعديل قبل اعتماد خطة التغيير.

### المرحلة C — التنفيذ المرحلي
- إكمال التقاط البيانات من مصدر الشبكة الفعلي.
- توحيد StreamSession وتمرير سياقها دون تسريب أسرار.
- إصلاح دورة حياة المشغل وتطبيق DataSource المناسب لكل جلسة.
- إضافة معالجة أخطاء HTTP وDRM المرخص.
- إضافة إدارة المصادر وتجديد API الحقيقي.
- تنفيذ اختبارات لكل طبقة قبل الانتقال إلى التالية.

### المرحلة D — البناء والتحقق
- بناء APK.
- zipalign والتحقق من التوقيع.
- تثبيت النسخة على الجهاز المستهدف.
- تجربة مصدر HLS ومصدر DASH ومصدر يحتاج جلسة مصرحاً بها، كلٌ على حدة.
- تسجيل حالات Manifest وSegments وLicense وPlayer state.
- اختبار 403 وToken expiry وIdle وBuffering.
- التحقق من عدم تراجع التصفح واللاقط والترجمات والتورنت.

## 7. معايير القبول

لا يُعتبر العمل مكتملاً إلا عند توفر أدلة على:
- التقاط رابط من الصفحة أو API مع سياقه الفعلي.
- عدم فقدان Query parameters الخاصة بالتوقيع أو انتهاء الصلاحية.
- تمرير الترويسات الصحيحة إلى الطلبات التي تحتاجها فقط.
- عدم خلط جلسات التبويبات أو المصادر.
- تشغيل HLS/DASH والترجمات المدعومة.
- التعامل الصحيح مع فشل HTTP وDRM المرخص.
- الانتقال إلى مصدر بديل أو الحصول على بيانات API جديدة عند الحاجة.
- عدم تكرار المحاولات بلا نهاية.
- نجاح البناء والتوقيع والتثبيت والتجربة الفعلية.
- عدم كشف الأسرار في السجلات أو التقارير.

## 9. الخلاصة

التقدم المحقق حتى الآن هو **تحديد تصميم مستهدف ومراجعة فنية لمواطن النقص والمخاطر**، مع مقارنة أولية بمصدر NovaBrowser الموجود على GitHub. أهم فجوة بين التصور والمصدر الحالي هي أن المشروع يملك بالفعل WebView وSniffer أساسيّاً وMedia3 Player، لكنه لا يملك في الملفات التي تمت مراجعتها منظومة API-session وCookie forwarding وDRM configuration وsource failover وAPI refresh بالصورة الكاملة المقترحة.

الخطوة الحاسمة التالية ليست كتابة كل المكونات دفعة واحدة؛ بل فحص APK المستهدف ومطابقته بالمصدر، ثم تنفيذ أصغر تغييرات مترابطة مع اختبارات قبول واضحة.
